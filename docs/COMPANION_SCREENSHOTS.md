# Companion photo library

Companion 0.14.0 provides a unified **Photo timeline**. The home banner opens the newest 30 photos across the stored library; **View all photos** opens the timeline. Game profiles retain their own galleries. Newest indexed capture time comes first, with a stable provider/game/photo tie-break. Capture dates come from the desktop index, not upload time.

## Browsing

The timeline loads 60 rows at a time and continues near the bottom. Show more remains as a fallback. Console filters operate on the complete stored catalogue; Through date jumps to photos captured on or before a chosen date, with All dates to clear it. Unknown capture dates stay unknown and appear last. Console chips use the desktop icons, scroll sideways, and prioritize the most populated consoles.

Comfortable/Compact density and Group photos are shared with game galleries. Grouping defaults off. When enabled, named and Ungrouped sections stay inside each capture date and separate game identity; the header includes the game title. Each section collapses independently. Filters, loaded pages, collapse state, focus and gallery scroll survive photo navigation. A full reload resets view state, while density/grouping choices remain browser preferences.

Thumbnails form filled square bands with balanced final rows. Timeline image sources outside an 800px viewport margin are released and restored on approach, retaining tile nodes and geometry. Incremental append uses indexed photo positions rather than repeatedly searching the entire collection. The home grid renders independently of the bounded recent-photo request.

The shared viewer opens uncropped viewing copies with information hidden. Tap toggles info and download actions; swipe down, Escape or browser Back dismisses. Horizontal gestures/arrow keys navigate loaded filtered photos. Next/previous replace history so dismissal returns to the timeline/home/gallery directly. Deep links resolve individual metadata outside loaded pages. Initial focus uses the hidden viewer title; pointer viewing has no focus/tap ring, while Tab focus remains visible. Original files are attachments with unchanged bytes, original names/types, ETags and ranges. Photos with external XMP have a separate **Download metadata (.xmp)** action.

The authoritative current folder inventory excludes 235 clips and stale index-only entries. All selected files were accessible; no missing formats were silently skipped. There are 94 JPEG XR captures and 18 external XMP files. Original descriptors total about 35GB; content-addressed storage deduplicates identical bytes without merging photo identities.

The exporter reads the desktop folder cache, index, storage groups and capture-group database without writes. It uses exact indexed IDs/timestamps and preserves assigned groups. Native storage families consolidate console editions; exact shared provider identity also consolidates duplicate folders, preserving memberships from each storage scope. Opaque photo IDs remain derived from workspace, edition and relative path; a future durable desktop asset ID is still needed for rename identity.

JPEG XR browsing copies use Windows Imaging Component and a bounded SDR tone map that preserves bright detail. Some WIC half-float formats appear as Default in WPF; the converter handles that case explicitly. The full-resolution JXR is retained unchanged, alongside any original XMP. Browsing derivatives are JPEGs capped at 480px/2560px long edge with rebuilt metadata. ## Intentional PC deletions — 0.16.0

Deleting through the existing Native PC library now removes that photo from web galleries, the timeline/home strip, game counts and direct media/download URLs after the stable automatic sync (normally about a minute after indexing settles). The PC connector reads the existing logs/PixelVault-native.log success record; the Native executable is unchanged. Failure messages, ordinary missing files, deleted/forgotten index rows, disconnected roots and incomplete inventory/index updates do not authorize a removal. Source state is rechecked immediately before posting. A same-path reimport must be present in both indexes under the same edition before it can restore that photo; a reassignment to another edition does not restore the old identity.

This is recoverable visibility reconciliation, not raw-file cleanup. The NAS stores removed photo metadata under screenshots/<workspace>/removals/<scope-hash>.json, retaining immutable previews/originals/sidecars. Prior overlay versions go to removal-history/. Later normal publication may drop the old raw catalogue row; its removal record still carries the metadata needed for restoration. Authenticated, versioned removal requests are scoped to existing published IDs in the paired workspace and obey Pause/Resume. All read surfaces apply the overlay, including cached/legacy catalogues. Old or pending uploads cannot bring a hidden photo back. The upload plan reports suppressed IDs so the current connector verifies the visible result correctly. Empty galleries are supported when the last photo is deleted.

Device APIs: GET /connector/v1/screenshots/removals; POST /connector/v1/screenshots/removals/{provider}/{game} with workspaceId, version, removeIds and restoreIds. The read-only --inspect-screenshot-removals <private-config> diagnostic prints only scoped opaque-ID plans, without credentials or source paths. Ordinary filesystem removals remain retained unless Native success evidence exists. A missing/cleared Native log cannot invent deletion intent. Hard deletion/space reclamation and a web trash interface remain separate work.

## Operation

**Connector 0.16.0 includes automatic photo sync** to the existing Windows sign-in connection. NAS/web is 0.16.0. Every 30 seconds it checks the current desktop folder inventory/index, assigned groups, original size/write time and optional XMP sidecar stamps. It waits for a stable observation before exporting an affected canonical game. New captures must first appear in the desktop index; this is not a replacement for desktop intake/indexing. A small change normally arrives within about a minute of indexing, plus export/transfer time.

Unchanged originals reuse the prior hash/preview only when size/write time and conversion version still match. Changed/new originals are hashed before and after export; new uploaded files are downloaded and hash-verified. Complete game metadata is checked after commit. Unchanged originals already on the NAS are not repeatedly downloaded. A post-export signature check defers files/index/group data still changing. Published missing-source photos and removed local sidecars retain their NAS copies; no deletion mirroring or desktop data writes occur.

The durable private automatic-photos.json checkpoint is saved only after successful publication/verification. Failed scopes remain unacknowledged and retry, normally after a minute; pause, loss of pairing, unavailable NAS/source, or quotas preserve the current NAS gallery. Existing Pause/Resume and library grants apply, including server checks on every mutation. The media worker has its own HTTP client/task, so heartbeat, trackers and achievements continue independently. A private exclusive screenshot-sync.lock prevents simultaneous manual and automatic exports. photo-sync-status.json and connector.log report local state without credentials/source paths.

Manual full verification remains available, but is usually unnecessary. Pause automatic updates before a manual full sync so it can acquire the shared lease. Manual --prepare-screenshot-library followed by --publish-prepared-screenshot-library requires an unchanged prepared ledger; reprepare after automatic changes if its scope/count check rejects it.

Use the existing private pairing file; never copy its token into source, notes or commands. Connector 0.15.0 also accepts --inspect-screenshot-library <private-config> for a read-only metadata poll (no original-byte reads). The manual tool accepts `--prepare-screenshot-library <private-config>` and then `--publish-prepared-screenshot-library <private-config>`. The ordinary `--sync-screenshot-library <private-config>` prepares and publishes together. Preparation records every selected original hash before/after conversion. Publication checks server capabilities, uploads missing assets, commits each game only after every reference is present, and downloads/verifies all published metadata, derivatives and originals. Interrupted uploads retain the last published game and retry idempotently. A failed library preparation does not publish its partial output.

The NAS option `Companion__ScreenshotLibraryEnabled=true` enables approved library-wide uploads. `ScreenshotPilot` remains backward compatible. Shared assets/originals live under the existing workspace root; per-game manifests use `catalogues/<scope-hash>.json`. The legacy Director’s Cut catalogue keeps its original location. Published photos absent from a later PC snapshot are retained; no deletion mirroring or raw-file eviction occurs. Stored photos remain readable if the PC is off, paused/revoked, or a game leaves the current desktop library. New uploads still require the current approved game identity and paired workspace.

Limits: 1,000 game catalogues, 5,000 photos per catalogue, 60 rows/page, 30 home thumbnails, 8GiB derivatives and 64GiB originals/sidecars in library mode; each derivative 6MiB, original 64MiB, XMP 1MiB. Old pilot quotas remain when library mode is disabled. All user media routes require owner authentication; connector routes require the existing device credential and enabled automatic/library controls. Original/metadata payloads are streamed and verified; XML is never rendered inline.
